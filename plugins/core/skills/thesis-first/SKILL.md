# 中心の一文から組み立てる

**中心の命題を1文で掴んでから、すべての要素をそこからの因果でぶら下げる。** 来た情報を来た順・種類別に並べる「羅列」を、既定の形にしない。

命題はたいていゴール（この文書・判断は何を実現するためか）。調べものなら「何を確かめたいか」、訂正なら「どの誤りを消すか」。何であれ1文で言えることが条件。

何をどう書くか（言葉づかい・見せ方）は writing-for-humans、関係の整理は structure-reading。ここは**どの順で組み立てるか**だけを持つ。

## 1. いつ使うか

- 材料が3つ以上の出どころから来ている
- 出来上がりが1画面に収まらない

一問一答・短い報告・1か所の修正には使わない（前置きが増えて、かえって読みにくくなる）。

## 2. 手順

1. **命題を1文で書く。** 書けなければ組み立てを始めない。材料が足りないのか、ゴールが決まっていないのかを先に解く（ゴールが決まっていないなら人に聞く。when-to-ask）
2. **出口を書く。** 何が満たされれば終わりか。できた・できていないで判定できる文にする
3. **骨格を引く。** 命題から出口までの段を3〜5本。それより多いのは骨格でなく目次
4. **要素を骨格に差し込む。** どの段の何のためにあるかを言えない要素は、捨てるか「範囲外」へ送る。集めた材料を全部使おうとしない
5. **新しい情報が来たら、どの段に効くかを先に決める。** 末尾に足さず、その段を書き換える。骨格が変わるなら命題から見直す
6. **仕上げに遡る。** 各見出し・各項目から命題まで遡れるか。命題に効かない項目が残っていないか

手順5が崩れどころ。情報が来るたびに末尾へ足すと、1回ごとは正しいのに全体は羅列に戻る。

## 3. 効かせる範囲

人に見せる文書だけでなく、次にも効かせる。

- ほかのAI（サブエージェント）への依頼文と、その報告を束ねるとき。束ねるときがいちばん羅列に落ちやすい。報告が N 本届くと N 個の節を作りたくなるが、骨格は依頼を出す前に引いてあるはずで、報告はその段に差し込む材料
- 引き継ぎのメモ、決定の記録（ADR）、プルリクエストの本文

## 4. この作法が見ないもの

- 命題が正しいかどうかは見ない（形の作法）。命題そのものを疑うのは premise-doubt
- 散文で書かれた羅列は、見た目では気づきにくい。手順6の遡りで拾う
