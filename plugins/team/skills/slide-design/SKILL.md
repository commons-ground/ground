# スライド作り（聞き手目線のストーリー → スライド）

返答・成果物はすべて日本語。人向けの言葉はシンプルに。比喩的な言い回し（「〜に響く」など）は避ける。

## このskillの作り方（土台と上乗せ）

このスキルは、外部のスキルを土台にして、**足りない部分と、変えたい部分だけ**を書いている（core の making-skills の上乗せの形）。土台のskillが更新されたら、その良さはそのまま使う。土台に書いてあることは、ここに書き写さない。

### 土台にするskill（先に読む）

| 使う場面 | 土台のskill | そこに任せること |
|---|---|---|
| どの形式でも（構成とデザインの基本） | 公式 **pptx** skill（anthropic-skills:pptx）の「Deck content and flow」「Design Ideas」「QA」の節 | 1スライド1メッセージ、ピラミッド構造、1枚あたりの時間の目安、レイアウト、避けるデザイン（見出し下の線、色の帯など）、画像にして確かめる手順 |
| .pptx を作る・直す | 公式 **pptx** skill 全体 | ファイルの作り方、ノートの入れ方、検証 |
| Googleスライドを作る・直す | **google-workspace** skill | 編集の手順 |
| Canvaで作る・直す | **Canva MCP のツール説明**（と、入っていれば Canva公式の canva-skills プラグイン：edit-design、implement-feedback、get-design-feedback など） | 新規作成の流れ（アウトライン確認→生成）、編集・保存の手順 |
| 配色とフォントの組み合わせを選ぶ（入っていれば） | **theme-factory** skill | テーマの候補 |
| 参加者に投げる問いの言葉 | team の **question-design** | 問いの言葉を磨く |
| 地域のデータ資料（各自のスキルにあれば） | 自分のスキル | データ資料と出典番号 |

土台のskillがこのセッションに無いときは、このskillの内容だけで進め、無かったことを一言伝える。

### 土台と食い違うときは、こちらを優先する

- **配色**：pptx skillは「大胆な配色」をすすめるが、ここではシンプルにする。色は少なく、意味を固定する（例：3つの立場に3色）。強調は1枚に1か所。
- **フォント**：日本語は BIZ UDPゴシック（自分ルールで別のフォントを決めていればそれに従う）。
- **文字だけのスライド**：pptx skillは「全スライドに図などを」とするが、問いだけのスライド、一言で間をつくるスライド（「でも」）、今日の流れ・お約束のスライドは文字だけでよい。
- **構成の順番**：pptx skillのピラミッド構造（結論を先に）は、ストーリーライン表を作るときの考え方として使う。話す順番は、聞き手の疑問の順に並べる。
- **作り始めるタイミング**：土台のskillやツールがすぐ作り始める流れでも、下の手順3の承認が済むまでスライドは作らない。Canvaのアウトライン確認は、承認済みのストーリーライン表をそのまま渡す場として使う。

## いちばん大事なこと（上乗せ部分の中心）

スライドから作り始めない。スライドを作ることに集中するとストーリーが描けず、スライドどうしが分断される。
**先にストーリーラインを作り込み、承認をもらってから、スライドに落とす。**

ストーリーは聞き手目線で書く。場面ごとに「聞き手が何を感じ、何を疑問に思うか」を書き、**次の場面がその疑問に答える**形でつなぐ。疑問でつながっていない場面があれば、そこが分断している場所。

この手順はどの場でも同じ。場の種類で変わるのは「必ず入れる場面」と「ノートの形」で、`references/patterns.md` から選ぶ。

## 手順

🧭 AI設定ページの自分ルール（このスキルの欄）があれば先に読む。配色・フォント・使う道具・過去の資料の置き場など、自分流の決めごとはそこに置く。

### 0. 受け取る

次をそろえる。わからないものだけ、まとめて1回聞く。

- 場：何の場か、持ち時間、会場、人数 → **パターンを決め、`references/patterns.md` の該当する節を読む**（組み合わせてもよい）
- 聞き手：誰か、来たときにどんな気持ちか
- 話す人：一人か、複数で掛け合うか
- 最後の行動：スライドのあと、聞き手に何をしてほしいか
- 配る物・使う物、根拠にできる一次資料、既存の資料、作る形式（Canva／pptx／Googleスライド）

### 1. 核と最後の行動を一文にする

「聞き手が帰るときに持って帰る一文」と「最後に聞き手がすること」を書く。この二つに向かわない場面は、削るか予備に回す。

### 2. 通しの糸を決める

聞き手が想像できる具体的なもの（暮らしの一場面、現場の一瞬、一つのキーワード、一枚の写真）を一つ選び、**冒頭で出し、途中で戻り、最後までつなぐ。**

- 糸を分解して全体の枠に使うと、後半の話も糸に戻って理解できる（例：一つの具体例を「3つの立場」に分け、後のデータもその3つで説明する）。
- 糸に色やアイコンを決めたら、最後まで同じ意味で使う。
- 冒頭の場面に最後で戻ると、話が閉じる。

### 3. ストーリーラインを表で書く（ここで一度止まる）

| # | 場面（この場面で言うこと＝一文） | 聞き手の気持ち・疑問（入る前） | この場面の答え・中身 | 通しの糸の出し方 | 根拠（出典） | 時間 |
|---|---|---|---|---|---|---|

確認すること：

- **つながり**：各場面の「聞き手の疑問」は前の場面が生んだものか。それに、この場面が答えているか。
- **気持ち**：不安や反発を生んだまま放っておく場面がないか。次の場面で具体的に答える。
- **パターンの必須場面**が入っているか。
- **時間**：合計が枠に収まるか。押したときに削る場面と予備を決める。

**別の目で読む**：見せる前に、表だけを別のエージェント（サブエージェント）に渡し、聞き手の立場で読んでもらう。渡すのは表と「聞き手は誰か・来たときの気持ち」だけにし、作った側の意図は渡さない。頼むこと：
- 疑問が残ったまま次へ進む場面、急に話が飛ぶ場面（分断）を挙げる
- 不安や反発が残る場面を挙げる
- わからない言葉、抽象的なお題目を挙げる
指摘を受けて表を直し、直したことを一言添えて見せる。

表を見せて承認をもらう。**承認の前にスライドを作り始めない。** 直しの依頼が来たら、まず表を直す。

### 4. スライドに落とす

デザインとレイアウトは土台のpptx skillに従い、次を上乗せする。

- **見出しはメッセージの文**にする。話題名（「地域の現状」「組織構成」）にしない（例：「亡くなる人が、生まれる人の約5倍」「初めて、生産者だけでイベントを運営した」）。問いのスライドは問いを見出しにする。
  - 長さは一目で読める長さに。**30字以内を目安**にし、2行を超えない。長くなるときは、言いたいことを一つにしぼるか、補足を見出しの下の小さい文に回す。
  - 根拠：見出しを文にし、本文を図などの証拠で見せる「アサーション・エビデンス型」は、話題名＋箇条書きより理解と記憶がよかったという研究がある（Garner & Alley ほか 2011・2013）。
- 見出しの下は、その文を裏づける証拠（大きな数字1つ、短いグラフ、図、写真、実物）。話す内容をそのまま画面に書かない。
- 出典は各スライドの下に小さく書く。
- 未確定の中身は［仮］と書いて仮のスペースを置き、誰が差し替えるかを書く。
- 使わないかもしれないスライドは「予備」と見出しに書いて最後にまとめる。出典一覧も最後に。

### 5. スピーカーノートを書く

基本の形（パターンによって足すものは `references/patterns.md`）：

```
【話す人】
【聞き手の気持ち】このスライドを見たときの気持ち・疑問
【話すこと】話す言葉（そのまま読めるくらい具体的に）
・補足、聞かれたら答える数字など
【つなぎ】次のスライドへの一言
【約○分】
```

- 1枚目のノートには全体の段取り：持ち時間、進め方、最初のひとこと、場面の並び、時間が押したら削るもの。
- 専門用語は、ノートで日常の言葉に言い換える。

### 6. 確かめて仕上げる

- 見た目の確認は土台のskill（pptx skillのQA、Canvaならサムネイル）で行う。
- 下の「数字と引用」と「仕上げの確認」を行う。

## 数字と引用（誤りゼロ）

- 数字・引用は一次資料だけから取る（統計、公的機関の文書、論文、団体の公式記録）。孫引きは使わない。見つからなければ「見つからなかった」と書き、数字を作らない。
- 別の資料（小冊子など）と組で使うときは出典番号をそろえる。
- 引用は原文のまま。最後に原文と一字一句照合する。
- 割合・倍率・「約○割」は元の数から計算し直し、丸め方を注記する。
- 仕上げ前に、数字と出典を別の目（サブエージェント）で一次資料と突き合わせる。

## Canvaで作るときの上乗せ

手順はCanva MCPのツール説明に従い、次を足す。

- Canvaで作る資料は、Canvaのデザインが正本。Canva MCPでできることは全部Claudeが行い、人に頼むのはAPIでできない操作だけにする。
- 作業の前に、既存のデザインの中身・ノート・サムネイルを読む。
- これまでに分かっている制約（ツールが更新されたら、ツール説明を優先する）：
  - 文字を追加するときにフォントを指定できない → 人が BIZ UDPゴシック に直す。そのスライドと箇所を一覧にして伝える。
  - 図形の中の文字は上揃えになる → 箱の高さで位置を調整する。
  - 編集のトランザクションは数時間で切れる → まとまった編集をしたら、すぐ保存する。
- **保存の前に、サムネイル（プレビュー）を見せて承認をもらう。**

## 仕上げの確認（上乗せ分のチェックリスト）

デザイン・文字のあふれなどの見た目のチェックは土台のskillのQAで行う。こちらでは次を確かめる。

- [ ] ストーリーライン表が承認済みで、スライドの並びが表と一致している
- [ ] どの場面も、前の場面の疑問に答えている／不安のまま終わる場面がない
- [ ] 通しの糸が冒頭・途中・最後につながっている
- [ ] 選んだパターンの必須場面がある
- [ ] ストーリーライン表を別の目（サブエージェント）で読み、指摘を反映した
- [ ] 見出しがメッセージの文（問いのスライドは問い）になっていて、30字以内・2行以内に収まっている
- [ ] 数字・引用がすべて一次資料と一致し、各ページの下に出典がある
- [ ] ノートの合計時間が枠に収まる
- [ ] ［仮］の箇所と、人が直す箇所（フォントなど）を一覧にして伝えた
- [ ] 比喩的な言い回し・抽象的なお題目（「持続可能な未来へ」など）を使っていない
